Incident Retrospective Agent

An AI agent that drafts outage retrospectives, scored against 5 companies' own root cause analyses.

Problem

Incident retrospectives follow a set structure: timeline, causes, impact and action items. That makes them a good use case for an AI agent. I built one to draft retrospectives from published outage timelines, and tested how well it works by scoring its findings against each company's own root cause analysis.

The build

The agent works in four steps. First, Claude Haiku lists every event in the timeline. Second, it identifies what contributed to the outage, quoting evidence from the timeline for each factor so every claim can be traced back. Third, it writes the impact and action items.

Step 4 is a reflection step: a second, stronger model (Claude Sonnet) reviews the draft against the original timeline. For each factor, it decides to keep it, remove it if the timeline doesn't support it, or merge it with a duplicate. It also tightens vague action items. Python code, not the AI, then applies those decisions and records every change, so the change log matches exactly what changed.

Evals

I tested the agent on 5 real outages: GitLab (2017), AWS S3 (2017), CrowdStrike (2024), Google Cloud (2025) and AWS DynamoDB (2025). For each one, I wrote an answer key from the company's own published analysis, and the agent never saw it. The agent ran 5 times per outage.

A second AI acting as a judge (Claude Sonnet) compared each factor with the answer key. Python code then calculated two scores: recall, the share of the company's published causes the agent found, and precision, the share of the agent's causes that were correct. Before relying on the judge, I tested it: I planted 5 wrong factors, and it caught all 5 in each of 3 runs. I also reviewed its decisions by hand on all 5 outages.

Results

The agent found 92–100% of each company's published causes, and none of the causes it listed were wrong. On CrowdStrike, some runs went further than the company's own findings. CrowdStrike's analysis focused on a faulty content update. In some runs the agent also pointed out that the software runs deep inside the operating system (at kernel level). That's why one bad update could crash entire computers instead of just the app.

What I learned

Having the same small model review its own work did nothing. It kept all 12 of 12 factors and logged changes it never made. Switching the reflection step to Claude Sonnet, and letting Python code apply its decisions, fixed both problems.

Twice, a low score turned out to be a scoring problem, not an agent problem. The agent had combined two causes into one point, and the judge could only credit one. I found this by reading the agent's actual answers instead of trusting the number. I also never changed an answer key after seeing the results to make a score look better.
